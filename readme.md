## 二、后端设计

### 2.1 框架设计
本项目需要支持至少6路的视频解析，为了保证摄像头之间的独立性、安全性采用多进程框架设计。其次由于单个摄像头的复杂功能需求，单个进程中采用多线程设计。
#### 2.1.1 多进程
多进程的设计分为两部分：管理器```Manager```与单个监控实例```Monitor```。其中管理器```Manager```通过读取配置文件启动需要的```Monitor```实例，并提供了如下表格的内置方法。

|     方法      |        简介        |     备注      |
|:-----------:|:----------------:|:-----------:|
| ```start``` |      启动所有进程      | 通常为第一次启动时使用 |
| ```stop```  |     强制停止当前进程     |      无      |
| ```start``` | 关闭异常终止进程并重新启动该进程 | 通常做运行时检查使用  |     

需要额外注意的是，进程之间目前不支持通信。若有不同的摄像头之间通信，其本质是将它们分属同一个进程然后进程内通信实现的。

#### 2.1.2 多线程
由于进程的一些限制，为了方便代码实现，实例```Monitor```使用函数方法实现。在实例```Monitor```中，需要注意的是还存在三个线程于后台强制更新，详细介绍如下表格。

|线程|        功能         |      备注       |
|:-:|:-----------------:|:-------------:|
|```Camera```| 读取流媒体并强制更新使其提供最新帧 | 内部提供流媒体断联恢复机制 |
|```Post```|   提交给业务后端需要的数据    |       无       |
|```VideoWriter```|  合成关键视频并提交给业务后端   |       无       |

更加详细的线程细节，详见```process.thread```或下文功能设计中。

### 2.2 功能设计
以下为实例```Monitor```中的算法逻辑后端功能。

#### 2.2.1 流媒体自更新
功能描述：opencv本身提供的视频流读取方法存在一个保护机制，即会将完整的流暂存下来，直至得到使用。由于算法的高耗时性，其运行帧率波动较大，出于内存、实时性的考虑，需要在线程中实时更新最新帧。其次，opencv本身仅提供短时的断联恢复，不符合该后端需要，需重写恢复机制。

功能要求：
- 1.使用opencv读取流并更新
- 2.设计长时间断联恢复机制
- 3.使用线程形式在类内启动，后台更新

功能设计：
- 1.设置类内字段`camera_open`值为`False`，使用opencv链接视频流，如果失败，回到1。如果成功，设置`camera_open`值为`True`。
- 2.读取视频流，读取成功，向类内通信队列`info`写入数据，其格式为`{'basic_info': 该摄像头身份信息, 'frame': 捕获的最新图片帧}`，回到2。读取失败，设置`camera_open`值为`False`，回到1。

#### 2.2.2 静默
功能描述：监控摄像头大多数时间捕获的画面为静止画面，即无人员进过，无环境变动（或极小），出于此事实情况，要求算法服务在画面中无人员经过、环境变动时，自动静默，以达到节省计算资源提高能效的目的。

功能要求：
- 1.无人员经过、环境变动时，算法后端自动静默 
- 2.人员常驻时需要继续检测 
- 3.不影响算法的正确性，并实现实时切换

功能实现：
- 1.设置行人锁`person_lock`状态为`False`，`person_count`值为`0`，将初始图片帧灰度化并记录到`pre_frame`。
- 2.运行时，将当前图片灰度化并计算与`pre_frame`图像绝对差异，小于一定阈值时，标记为画面处于`静态`，更新`pre_frame`。
- 3.检测画面中是否有行人，如果有行人，更新`person_lock`状态为`True`，并标记`person_count`值为`0`，算法继续运行。 若无行人，`person_count`值加`1`，若`person_count`值小于配置文件中的阈值，算法继续运行，若大于，标记`person_lock`状态为`False`，跳过算法，回到2。
- 4.执行检测、识别等算法。

详细代码细节见`process.Monitor`中的`silent_detection`函数与`Monitor`函数中初始化与循环开始阶段。

#### 2.2.3 行人跟踪
功能描述：完成基础的行人跟踪任务，并额外给出逻辑后端需要的信息，比如跟踪的轨迹，轨迹是否越线，有哪些跟踪id已经过期等算法后端需要的信息。

功能要求：
- 1.提取当前画面中的所有行人信息，包括如下表所示的信息。

|字段|       类型        |              备注              |
|:-:|:---------------:|:----------------------------:|
|`person_roi`| `numpy.ndarray` |         从全图中裁剪出的行人图片         |
|`embed`| `numpy.ndarray` | 使用`person_roi`提取的用于reid的外观特征 |
|`track`|     `List`      |    存储的该行人id的最近30帧人体中心点轨迹     |
|`movement`|    `string`     |        行人最近30帧的整体前进方向        |
|`crossed`|     `bool`      |          行人是否跨过穿越线           |
|`xyxy`|     `tuple`     |          该行人在原图中的坐标          |
|`reid`|      `int`      |          初始值为行人的id           |
|`color`|     `tuple`     |         为reid预留的颜色匹配         |
- 2.记录过期的id列表

功能实现：
- 1.初始化`track_history`为`defaultdict(lambda: [])`用于做跟踪记录，初始化`missing_frames`为`defaultdict(int)`用于记录每个id连续未出现的帧数。
- 2.进行yolo跟踪，提取出当前的id列表`current_ids`与记录的id列表`previous_ids`。
- 3.使用`current_ids`对`missing_frames`进行更新，使其值为0。
- 4.使用`previous_ids`减去`current_ids`得到未出现的id，对这些id值更新使其在`missing_frames`值加1。
- 5.检查`missing_frames`，当其中id值大于阈值（外部给定）时，认为其过期，记录到列表`drop_ids`中，并释放其在`track_history`与`missing_frames`中的记录。
- 6.使用`current_ids`提取`person_roi`.
- 7.使用`current_ids`更新`track_history`已记录当前id的当前中心点，获得轨迹。若大于30帧，去除第一帧，仅保留最近的30帧。
- 8.计算行进方向与是否跨越检测线，算法详见`utils.function`中的`check_movement`函数。
- 9.提取并整理备用信息，格式为`{id:dict}`，其中id为行人id，dict包含上表中的所有信息。
- 10.将行人信息使用字段`person_info`添加到data中，将过期id使用字段`drop_ids`添加到data中。注意，data为从`流媒体自更新`线程通信队列中获取的原始数据，其包含部分信息，详见上文。

#### 2.2.4 人脸识别
功能描述：基于监控采集的画面完成对人脸的识别，并标记陌生人以及相关信息。需要额外注意，行人身份一经确认不需要再次识别，以此降低算法负载，获得更好的实时性。

功能要求：
- 1.制作简单的特征库用于查比
- 2.动态捕获人脸特征，利用特征库比对，综合阈值判断是否为陌生人

功能实现：
- 1.加载特征名称到`names`，加载特征到`features_matrix`。初始化`tracking_records`为`{}`。
- 2.根据`data`中的`drop_ids`，释放`tracking_records`的相关记录。
- 3.根据`data`中`person_info`的id值查找`tracking_records`中是否已经有记录。若有记录且状态已经被确定，使用记录中的名字并结束。
- 4.若有记录且`name`的值为`Stranger`，对其进行间隔25帧检测一次的操作。若无记录，向其中插入一条`{id:{'name': "Detecting...",'retry': 0,'count': 0,'verified': False}`的记录。其详细作用如下表。

|   字段    |    类型     |               作用               |
|:-------:|:---------:|:------------------------------:|
| `name`  | `strring` | 记录id的名字用于查询，初始化为`Detecting...` |
| `retry` |   `int`   |        记录当前id识别时已经尝试的次数        |
| `count` |   `int`   |     用于降低无法识别陌生人的识别负载（计数器）      |
|    `verified`     |  `bool`   |         标记这个id是否已经识别完成         |

- 5.查询记录，将`count`值重置为0。提取人脸特征并在库中比对。若识别成功，更新`name`与`verified`。若识别失败，将识别次数`retry`值加1。 随后判断其是否已经大于阈值（配置给定）。若大于，标记`name`为`Stranger`。

#### 2.2.6 识别结果上传
功能描述：将已经识别或初步处理得到的结果提交到业务后端，需要注意的是不能由于网络请求的不稳定性导致进程卡顿。

功能要求：
- 1.采用后台线程运行的方式进行提交
- 2.不要多次提交重复数据增加业务后端的接口负载
- 3.过滤无效数据

功能实现：
- 1.初始化`tracking_records`为`{}`。
- 2.根据`data`中的`drop_ids`，释放`tracking_records`的相关记录。
- 3.根据`data`中`person_info`的id值查找`tracking_records`中是否已经有记录。若无记录，插入该条记录。若数据属于无效数据，标记字段`filter`为`True`。
- 4.若有记录，判断该条记录与上一条是否一直，若一致则过滤，标记字段`filter`为`True`。否则跟新记录，标记字段`filter`为`False`。
- 5.筛选`tracking_records`中字段`filter`为`False`的数据并提交。

#### 2.2.7 关键视频合成 
功能描述：对于一些异常监控需要合成为视频保留，需要注意的是不能由于视频合成的不稳定性导致进程卡顿。

功能要求：
- 1.采用后台线程运行的方式进行提交
- 2.保留异常视频点的前n帧和完整异常段
- 3.异常出现先提交到业务后端，后再合成视频

功能实现：
- 1.无行人通过时记录前n帧
- 2.有行人通过时判断是否为异常帧。若不是记录到前n帧列表中。若是开始合成，并提交异常信息。
- 3.当没有行人通过时，结束合成。
